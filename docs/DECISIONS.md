## D-02 The hook is the Aqua taker and pays by transfer
- Status: Decided, mechanism to verify in F02
- Why: SwapVM's taker trait `useTransferFromAndAquaPush` makes the router pull the taker's input and push it into the maker's Aqua balance, so the hook needs no taker callback. This avoids the riskiest callback-inside-unlock path.
- Verify against the swap-vm v1.0.2 source (the deployed router): which contract calls `transferFrom` on the taker, that the trait exists under that name, and that no rule requires the taker to be `tx.origin`. Priya's program must contain no `tx.origin`-based Controls guard.
- Still the top risk after D-13: Extruction does not change who the taker is. Ask mentors at hour 1.
- 1inch confirmed (Nov 5): a contract can be the taker, calling the router from inside another protocol's callback such as a v4 hook's beforeSwap. Still to verify in F02 from the v1.0.2 source: which address the router transferFroms, and any tx.origin or reentrancy restriction.
- F02 verified (Nov 6), v1.0.2 source and a fork trace:
  - The router pulls the taker's input (`SwapVM.sol:235`), so the hook approves the **router**, not Aqua. The router approves Aqua and calls `push`, which forwards the tokens to the maker's wallet (`Aqua.sol:78`). Trait name confirmed: `useTransferFromAndAquaPush`, flag `0x0040` (`TakerTraits.sol:58,99`).
  - Output goes through `AQUA.pull`, which does `transferFrom(maker, to)` (`SwapVM.sol:286`, `Aqua.sol:68`), so the maker approves Aqua.
  - No `tx.origin` rule on the taker. The only `tx.origin` use is the opcode `_onlyTxOriginTokenBalanceNonZero` (`Controls.sol:125`); Priya's program must not include it.
  - Reentrancy: a transient lock per order hash (`SwapVM.sol:164`). It blocks only re-entry on the same order, and a revert clears it, so the hook's try/catch is unaffected.
  - Not covered by F02: running inside `beforeSwap`. `test_F02_takerContractSwap` proves the token path from a contract taker; F05 proves it inside the hook.

- Note for F03: swap-vm has two interfaces in `src/instructions/Extruction.sol`: non-view `IExtruction.extruction` (swap) and `IStaticExtruction` (quote). One `view` function with the same signature satisfies both.
- F02 verified (Nov 6), v1.0.2 source and read-only calls to the deployed router at `FORK_BLOCK`:
  - `swap` and `quote` both take `(ISwapVM.Order order, address tokenIn, address tokenOut, uint256 amount, bytes takerTraitsAndData)` and return `(amountIn, amountOut, orderHash)` (`ISwapVM.sol:38-61`). `ISwapVM.quote` is `view`, so calling through the interface is a STATICCALL.
  - `takerTraitsAndData`: a 22-byte header (`uint160` of ten 16-bit slice end-offsets, then `uint16` flags), then `threshold(32 or 0) | to(20 or 0) | deadline(5 or 0) | hook data x4 | callback data x2 | instructionsArgs | signature` (`TakerTraits.sol:139-159`). Build it with `TakerTraitsLib.build`.
  - The strategy passed to `ship` is `abi.encode(order)`. `ship` hashes it with keccak256 (`Aqua.sol:41`), and the router's `hash` for Aqua orders is `keccak256(abi.encode(order))` (`SwapVM.sol:99`). The two match on the deployed router.
  - Runtime opcode indices: `_xycSwapXD` 17, `_salt` 20, `_flatFeeAmountInXD` 21, `_extruction` 32, `_onlyTxOriginTokenBalanceNonZero` 33; the table has 34 entries. `_opcodes()` overwrites array element 0 with the length (`AquaOpcodes.sol:79-83`), so runtime index = source position - 1. Code still looks indices up rather than hard-coding them.
  - The flat fee is `Fee._flatFeeAmountInXD`, scaled 1e9 = 100% (`Fee.sol:17`), so 0.30% is `3_000_000`. It runs the rest of the program inside itself (`Fee.sol:86-91`). See D-15 for what that means for F03.

## D-13 Use the canonical AquaSwapVMRouter; the band is an Extruction target
- Status: Decided (Nov 5, on 1inch's recommendation at the event)
- Decision: no forked or redeployed SwapVM. Priya ships her strategy with `app` = the deployed `AquaSwapVMRouter` v1.0.2 (`0x111111338c5091e8440b67b168bae16a668ac0de`). The band check is `PoolPriceBandExtruction`, an external contract that her program calls through the Extruction opcode (1inch's "Path C").
- Why: 1inch recommended it. It removes our riskiest Aqua-side work (fork, opcode table, version drift, redeploy). It meets "official Aqua/SwapVM contracts" fully. It also makes the band a reusable module any maker can attach to any strategy with no redeploy.
- Rules from 1inch's Extruction docs: the target must be non-upgradeable, and `quote()` and `swap()` must return identical amounts. We meet both with one stateless `view` function.
- Consequences: ConfluenceRouter is deleted from the plan. F03 shrinks to one contract and its tests. D-03 superseded, D-11 closed.
- 1inch confirmed (Nov 5): projects must use the official contracts, not their own swap-vm implementation.

## D-14 The band reads live pool state; quote/swap consistency holds within one transaction
- Status: Decided (Nov 5)
- Issue: 1inch lists block-state reads as a source of quote/swap mismatch. Our target reads `slot0`.
- Why it is safe for our path: inside `beforeSwap` the pool curve has not run yet, so `slot0` is the same for the hook's quote and its swap. F03 tests `quote == swap` in one transaction.
- Limitation, stated in the README: an outside taker who quotes in one block and swaps in a later one may find the quote stale if the pool price moved. Their swap then reverts or fills at the newly checked price. It is never filled outside the band.

## D-15 F02 test helper shape; the band sees the net-of-fee input
- Status: Decided (Nov 6) for the helpers; the band note is for F03 to act on
- `StrategyLib` is an `abstract contract` inheriting `AquaOpcodes`, despite its name. `_opcodes()` and the instruction pointers are internal, so a library cannot reach them. swap-vm's own `AquaStrategyBuilders` uses the same pattern with `AquaOpcodesDebug`; ours uses the non-debug table the router runs. It imports `ProgramBuilder` from `@1inch/swap-vm/test/utils/`, which emits one compiler warning located in that lib file (function-pointer comparison).
- `TakerHelper` follows the hook's flow: funded by `deal` where the hook would `take`, approves exactly `amountIn` to the router, receives the output itself (`to` = zero), resets the approval, then forwards the output where the hook would `settle`. `isFirstTransferFromTaker = false`, matching ARCHITECTURE section 3 step 7.
- For F03: with `fee, curve, Extruction`, the Extruction step runs inside the fee's nested `runLoop`, which runs to the end of the program, so no step can run after the fee returns. On exact input the registers hold `amountIn` net of the fee, so the band checks `(a - fee) / b`, not `a / b`. ARCHITECTURE section 3 step 7 and section 5 ("`bandBps` must exceed Priya's fee plus her curve's slippage") need correcting in F03: the fee does not use up band width, and a taker's gross price can sit up to one fee beyond the band, on the side that favours Priya. F03 tests must compute the expected execution price from the net input.

## D-16 PoolPriceBandExtruction validation, and the F03 [VERIFY] answers
- Status: Decided (Nov 6)
- Added beyond the F03 spec, approved by the team:
  - `InvalidArgsLength(uint256 length)`: `parse` requires exactly 88 bytes. Without it, short args revert with no named error and extra bytes are silently ignored.
  - `InvalidBand` fires in `build` as well as `parse`. `build` fails fast before a strategy ships; `parse` still checks because strategy bytes can be hand-built.
- Choices the spec left open:
  - `build` and `parse` live on the contract as `pure` functions, so F09 scripts can call them on the deployed contract.
  - `bandBps` is a `uint16` in `PoolPriceBandExceeded`, matching its 2 bytes in the args.
- Corrections to ARCHITECTURE section 5, now applied there:
  - The not-computed check runs before the price maths. In the old order, a misordered MUMB->USDC program divides by a zero `amountOut` and reverts with no named error.
  - The band comparison is `diff > mulDiv(poolX96, bandBps, 10_000)`. For integers it is equivalent to `diff * 10_000 > bandBps * poolX96`, which can overflow when `execX96` is near 2^256.
- F03 [VERIFY] answers, from the v1.0.2 source and a throwaway probe against the deployed router and PoolManager at `FORK_BLOCK`:
  - The Extruction opcode is index 32 (`AquaOpcodes.sol:73`, looked up at runtime) and it ran on the deployed router. A step is `opcode | argsLength | target | args` (`VM.sol:124-127`). Ours is `0x20 0x6c` then 108 bytes, 110 in total; `argsLength` is one byte, so at most 255.
  - `IExtruction` and `IStaticExtruction` have the same signature (`Extruction.sol:17-52`). `SwapQuery` and `SwapRegisters` field order matches ARCHITECTURE section 5 (`VM.sol:33-54`). One `view` function overriding both compiles and runs in `swap` and `quote`.
  - `XYCSwap` is not terminal: it never writes the program counter (`XYCSwap.sol:17-33`). The spec's "place the step where the registers hold the final amounts the taker sees" cannot be met for `amountIn`: the fee restores the gross input only after its nested `runLoop`, which runs to the end of the program (`Fee.sol:86-91`), and a fee after the curve reverts `FeeShouldBeAppliedBeforeSwapAmountsComputation` (`Fee.sol:83`). At the step, a 1,000 USDC swap shows `amountIn` 997000000 and `amountOut` 987158034397061298850. This confirms D-15.
  - `getSlot0` works during an unlocked session: `extsload` has no lock modifier (`Extsload.sol:10`). The probe read the same `sqrtPriceX96` inside `unlock` as outside it on the live PoolManager, with `isUnlocked()` true inside, and also read it from an Extruction target in the router's `quote` STATICCALL. An uninitialised pool reads 0. The probe was not committed, so no repo test covers the read inside `unlock` until F05.

## D-17 The hook implements `IHooks` directly; the `BeforeSwapDelta` sign convention (F04 [VERIFY])
- Status: Decided (Nov 6)
- No `BaseHook`: the F04 spec says to extend v4-periphery's `BaseHook`, but `lib/v4-periphery` (c6e4754, `heads/main`) has no `BaseHook.sol` and no `src/utils/`; a search of all of `contracts/lib/` finds none. `ConfluenceHook` implements `IHooks` itself: `beforeSwap` is live behind `onlyPoolManager`, the other 13 callbacks revert `HookNotImplemented` (the pattern of `lib/v4-core/src/test/BaseTestHooks.sol`, which we do not inherit because it is a test helper), and the constructor calls `Hooks.validateHookPermissions` (`Hooks.sol:82`), as `BaseHook` did. No new submodule (approved by the team). The F04 spec line is corrected.
- Sign convention, exact input: a hook that consumed input `a` and provided output `b` returns `toBeforeSwapDelta(+a, -b)`, i.e. specified = `+a`, unspecified = `-b`. This is what ARCHITECTURE section 3 step 9 says, now confirmed against the source:
  - `lib/v4-core/src/test/CustomCurveHook.sol:42-43`: `manager.take(input, hook, amount)` then `output.settle(manager, hook, amount, false)`.
  - `CustomCurveHook.sol:46`: returns `toBeforeSwapDelta(int128(-params.amountSpecified), int128(params.amountSpecified))`. On exact input `amountSpecified = -a`, so that is `(+a, -a)`.
  - `Hooks.sol:272-276`: `amountToSwap += hookDeltaSpecified`, so the pool curve swaps `-(|amountSpecified| - a)`; it reverts `HookDeltaExceedsSwapAmount` if that flips the sign, so `a <= |amountSpecified|` is enforced by v4 as well.
  - `Hooks.sol:305-309` and `PoolManager.sol:222`: the hook delta is accounted to the hook address (the `take` of `a` nets against `+a`, the `settle` of `b` against `-b`) and subtracted from the trader's `swapDelta`.
- Limit of this check: `CustomCurveHook` fills the whole amount. The partial case follows from the `amountToSwap` line above but is not exercised by a repo test until `test_F05_fullAquaFill` and the split tests. A wrong sign makes the PoolManager revert, so F05 will show it at once.
- F04 hook skeleton: also confirmed on the fork that a hook with `beforeSwapReturnDelta` set and a zero delta leaves swaps unchanged (`test_F04_beforeSwapZeroDeltaSwapEqualsNoHookSwap`).

## D-18 F04 hook interface details the spec left open; anchor price; seed
- Status: Decided (Nov 6)
- Constructor `(IPoolManager, address router)`. Events `OrderRegistered(PoolId indexed poolId, address indexed maker, bytes32 orderHash)` with `orderHash = keccak256(abi.encode(order))` (the Aqua-order hash, per `ISwapVM.hash`'s NatSpec), and `OrderUnregistered(PoolId indexed poolId, address indexed maker)`. Errors `NotMaker`, `NotPoolManager`, `NoOrder`, `HookNotImplemented`. A getter `orderOf(PoolId)` returns the stored `ISwapVM.Order` (`maker` is zero when none). `unregisterOrder` checks `NoOrder` before `NotMaker`.
- `registerOrder` replaces any earlier order for the pool, whoever registered it (D-09: one order per pool). Only `order.maker == msg.sender` is checked, so a second maker can displace the first. This can switch off the Aqua leg for that pool, and never fails a swap. **Amended by D-20 (F06):** it can also make a swap cost more gas, because a registered strategy can burn all the gas the hook forwards to the router. The forward is capped at `MAX_AQUA_GAS` (640,000), so the cost to a trader is bounded and the swap still passes. A very large `order.data` also costs gas on every swap, to load from storage and to encode into the router call. **Amended again by D-20 (order size limit, Nov 6):** `registerOrder` now reverts `OrderDataTooLarge(length, max)` above `MAX_ORDER_DATA_BYTES` (512), so that cost is bounded. The displacement issue is unchanged and stays a known limitation: any maker can still replace the active order and switch off the Aqua leg for that pool.
- Anchor price, 1 MUMB = 1 USDC (the second F04 [VERIFY]): v4 price is raw currency1 per raw currency0. With USDC as currency0, price = 1e18 / 1e6 = 1e12, so `sqrtPriceX96 = 1e6 * 2^96`. With MUMB as currency0, price = 1e-12, so `sqrtPriceX96 = 2^96 / 1e6`. Both are exact square roots. The currency order depends on `address(mumb)`, which depends on the deployer nonce, so the test base branches on it; at `FORK_BLOCK` USDC (0xA0b8...) is currency0. The anchor ticks are about +/-276,324 (`test_F04_anchorPriceBothOrders`).
- Seed position: 2,500 USDC and 2,500 MUMB offered, over the anchor tick rounded to spacing 60 plus and minus 600 ticks (about +/-6%), liquidity from `LiquidityAmounts.getLiquidityForAmounts`. A 1,000 USDC pool-only buy moves the tick from 276,324 to 276,080 (about 2.4% in price), which stays in range, and returns 984.934194542570551127 MUMB. F05 to F08 should expect a pool swap of that size to move `slot0` by more than a 200 bps band.

## D-19 F05: the Aqua leg inside the hook
- Status: Decided (Nov 6)
- Result: `test_F05_fullAquaFill` passes, so the hook can be the Aqua taker on the canonical router inside `beforeSwap`. Hour-8 gate met; F05-ALT is not needed. D-02's "not covered by F02" item is closed.
- Checked in the source (v4-core and swap-vm v1.0.2):
  - `take` and `settle` need only an unlocked PoolManager (`PoolManager.sol:289-304`) and book deltas to the caller, the hook. The returned `BeforeSwapDelta` is booked to the hook (`PoolManager.sol:222`) and subtracted from the trader's delta (`Hooks.sol:311`), so the hook's `-a` (take) and `+b` (settle) net against `+a` and `-b`.
  - `take` is a real transfer out of the PoolManager's global balance, so it needs `a` on hand. USDC is always there. MUMB is ours, so the PoolManager holds only the seed's MUMB (2,500e18): a MUMB-input hint above that reverts the swap in F05. The band caps one fill at about 2,006 MUMB, so demo sizes fit. F06 must guard it.
  - The router's taker is `msg.sender`, the hook (`SwapVM.sol:179`); the output goes to the hook because `to` is zero (`SwapVM.sol:266`). The per-order lock (`SwapVM.sol:164`) trips only if the same order re-enters; F06's try/catch turns that into a pool-only fill.

  - `CurrencySettler` comes from `v4-core/test/utils/` (the helper `CustomCurveHook` uses). Nothing else in the repo settles.
  - Skip checks run cheapest first: exact output or `hookData` not 32 bytes, then `a == 0` or `a > |amountSpecified|` (computed without overflow at `int256.min`), then no registered order.
  - The minimum output passed to the router is 1; the trader's price limit and the band are the real protection.
  - OpenZeppelin `SafeCast.toUint256` (aliased `OZSafeCast`) for the `int256` to `uint256` step; v4's `SafeCast` has none. Two forge-lint disables, each with its reason: `unused-return` (only `b` is used; the router's check makes the amount in equal `a`) and `reentrancy-events` (`b` is known only after the call).
  - `AquaSkipped` is not in F05: skips are silent, and F06 designs the event with the router's revert data.
- Partial fills confirm D-17's sign: `(+a, -b)` with a hint below the swap amount, and in both directions.

## D-20 F06: Aqua can never fail a swap: unwind, skip cases, gas
- Status: Decided (Nov 6). Implements D-06.
- Result: the five acceptance tests and ten extra tests in `F06Safety.t.sol` pass (15); `forge test` passes 64 (49 earlier + 15). `spec-reviewer` found every Behaviour and Acceptance line met.
- Unwind: the router call is inside `try`/`catch`. A router failure undoes everything the router did, so the hook holds exactly the `a` it took. It resets the approval to 0, settles `a` back to the PoolManager, emits `AquaSkipped(poolId, reason)` and returns a zero delta. Only the router call is inside the try: the settlement of `b` after a success, the `b.toInt128()` cast and the decoding of the router's return are not.
- Skip events (the spec left this open). A swap that asked for an Aqua leg, meaning a non-zero 32-byte hint, and is skipped emits `AquaSkipped`. A swap that did not ask (empty or other-length `hookData`, or a hint of 0) is pool-only and silent, so ordinary pool swaps add no log. Pre-call checks, cheapest first: exact output (`ExactOutputNotSupported`), hint above the amount (`HintAboveAmount`), hint above int128 max (`HintTooLarge`), no order (`NoOrder`), PoolManager holds less of the input token than the hint (`PoolManagerShort(available)`, which F05 left as a revert), `gasleft()` under `AQUA_GAS_RESERVE + MIN_AQUA_GAS` (`InsufficientGas(gasLeft)`). `reason` is an ABI-encoded custom error; for a router failure it is the router's own revert data.
- Revert data is trimmed to `MAX_REASON_BYTES` = 256 (`returndatacopy` of a bounded prefix, not `catch (bytes memory)`). `registerOrder` accepts any maker (D-18), so the revert data of a maker-chosen Extruction is untrusted; the event would cost 8 gas per byte and the copy more. Out of gas leaves no data, so the reason is empty.
- Checked in the source:
  - Docked strategy: `Aqua.dock` stores `(0, DOCKED)` (`Aqua.sol:54-61`); `safeBalances` then reverts `SafeBalancesForTokenNotInActiveStrategy(maker, app, hash, token)` (`Aqua.sol:32`), and the router calls it first (`SwapVM.sol:194`), before any transfer.
  - "Hint larger than her virtual balance": the XYC curve gives `amountOut = in * balOut / (balIn + in)` (`XYCSwap.sol:22-24`), always below `balOut`, so a fill can never overdraw her virtual balance and the underflow in `Aqua.pull` (`Aqua.sol:66`) is unreachable. What refuses such a hint is the band (`PoolPriceBandExceeded`); `test_F06_insufficientMakerBalanceFallsBack` tests that. The real balance failure is her wallet holding less than her virtual balance, so `test_F06_makerWalletShortFallsBack` was added.
  - Revoked approval and short wallet both fail in `Aqua.pull`'s `safeTransferFrom` (`Aqua.sol:68`), through 1inch's `SafeERC20`, which reverts `SafeTransferFromFailed()` rather than passing the token's error up.
  - Order of events in `swap` (`SwapVM.sol:156-215`): lock, safeBalances, program (band), transfer out (pull), transfer in. A failure at any point reverts all of it.
- int128. Two conversions. The hint `a` is checked against int128 max before anything is taken (`HintTooLarge`). `b.toInt128()` runs after the router call, outside the try/catch, and is accepted. It is not enough to say `b` is at most a `uint248` (Aqua's balance type): `uint248` is larger than `int128`, so that does not prove `b` fits. The reason is that the band holds the fill to roughly `a` times the pool price and `a` is already capped at int128 max, so `b` can overflow only at an absurd pool price. A revert there reverts the whole swap, with no tokens stranded.
- Gas. The router gets `min(gasleft - AQUA_GAS_RESERVE, MAX_AQUA_GAS)`, and the hook skips Aqua when `gasleft` is under `AQUA_GAS_RESERVE + MIN_AQUA_GAS` at the check. Constants (all `public constant`): `AQUA_GAS_RESERVE` 150,000, `MIN_AQUA_GAS` 160,000, `MAX_AQUA_GAS` = 4 * `MIN_AQUA_GAS` = 640,000. Why a cap is needed at all: with no cap, the 63/64 rule leaves the hook about 1/64 of the gas at each call level, and a strategy that burns its gas starves the rest of the swap.
- Measurements and method:
  - `MIN_AQUA_GAS`: gas of the router call in `test_F05_fullAquaFill` 152,432, `test_F05_partialSplit` 152,432, `test_F05_reverseDirection` 153,418 (from `forge test -vvvv`, identical with `--isolate`). The largest, rounded up to the next 10,000, gives 160,000. The hook's own work around the call (`take`, `approve`, set-up, unwind, event) is about 106,000 (`beforeSwap` 258,598 less the call).
  - `AQUA_GAS_RESERVE`: a scratch probe, not committed, with the reserve temporarily a storage variable set with `vm.store`. For each reserve and each transaction gas limit it ran the pool-only swap and the hinted swap from the same snapshot with `swapRouter.swap{gas: limit}`, for two strategies (Priya's legitimate fill; `GasBurnExtruction`, which executes `INVALID`). The criterion is that the hinted swap never reverts where the pool-only swap passes. Pass 1: 24 limits from 285,000 to 3,000,000. Pass 2: 52 limits, 285,000 to 500,000 in steps of 5,000 plus 550,000, 600,000, 700,000, 800,000, 1,000,000, 1,500,000, 2,000,000, 3,000,000.
  - Results: reserve 70,000 reverts at 17 of 24 limits for the burning strategy (310,000 to 1,000,000) and 4 for the legitimate one (320,000 to 360,000). Reserve 100,000 reverts at 10 limits (335,000 to 380,000) and 13 (345,000 to 405,000) of 52. Reserves 105,000, 110,000, 115,000, 120,000, 125,000 (and 130,000, 160,000, 200,000, 250,000 and 300,000 in pass 1) revert at none. The measured need is 105,000; 150,000 is that plus 43%.

## D-22 F08: how the invariant handler models Priya, the band check and the ghosts
- Status: Decided (Nov 6). The F08 spec left these open ("Priya docks and re-ships" and "value conserved" need a precise meaning). `fullAquaFillAnchorRecovers` was finished with its main approach inside its timebox, so the fallback (opposite-direction pool-only swaps) was not used.
- Re-shipping needs different strategy bytes. Aqua's `ship` refuses a hash whose tokens already have a non-zero count (`lib/aqua/src/Aqua.sol:48`), and `dock` leaves the count at `0xff`, not 0 (`Aqua.sol:58`), so shipping the same bytes again reverts. The strategy hash is `keccak256` of the order (`Aqua.sol:41`; the amounts are not in it). The handler prefixes the program with `Controls._salt` (a no-op opcode in the canonical set, `AquaOpcodes.sol:61`, `Controls.sol:70`) holding a counter, so each re-ship has a new hash. `test_F08_saltChangesHashNotOutput` shows that the salt changes the hash and changes no amount of a 1,000 USDC full fill.
- Redock design: Priya docks, then ships 10,000 to 100,000 MUMB with **USDC = MUMB x the pool's current price** (three times in four), so her curve starts at the pool's price; a maker who re-ships to where the market is. One time in four she ships at the anchor price, 1 MUMB = 1 USDC, which is stale once the pool has moved. Random USDC amounts were rejected: her curve would sit far outside the 200 bps band and Aqua would be refused for the rest of the run, so the invariants would only ever see skips.
- `makerValueConserved`, precisely. `ship` writes a virtual balance and moves no tokens, and `dock` zeroes it and moves no tokens (`Aqua.sol:49`, `:58`); only `pull` and `push` move wallet tokens, and each changes the virtual balance by the same amount (`Aqua.sol:66-68`, `:74-78`). So "wallet change equals virtual balance change" holds per token only when the virtual change is summed over every strategy she shipped, counting the balance just before the dock for a docked one, minus what she shipped. The handler keeps those as ghosts (`Strategy` records) and the invariant compares them with her wallet change since the handler was built.
- `noAquaFillOutsideBand` uses its own copy of the extruction's maths, with its rounding: the input is the fill's `amountIn` net of the 0.30% fee (`a - ceilDiv(a * fee, 1e9)`, as `Fee.sol:89`), `poolX96 = mulDiv(s, s, 2^96)`, `execX96 = mulDiv(out, 2^96, net)` when currency0 is the input and `mulDiv(net, 2^96, out)` otherwise, and the fill is inside the band when `diff <= mulDiv(poolX96, bandBps, 10_000)` (`PoolPriceBandExtruction.sol:63-77`). `s` is the pool price read just before the swap, which is the price `beforeSwap` reads, because the pool curve runs after the hook (ARCHITECTURE section 3). `AquaFill` carries no price, so the check rebuilds it from `amountIn`, `amountOut` and the direction.
- Price stays in the seed range. Every handler swap has `sqrtPriceLimitX96` at the seed range's bound in its direction, and a swap whose limit is already passed is not made, so there are no `PriceLimitAlreadyExceeded` reverts and the price never leaves the liquidity. A swap that reaches the limit fills partly, which v4 allows.
- Hints are on a 1% grid, 1% to 100% of the input, plus 0 and 100%. A raw random hint gave dust (a sample was 1,977 wei of MUMB) whose output rounds to zero; our own `PoolPriceBandExtruction` reverts `PoolPriceBandNotComputed()` for a zero `amountIn` or `amountOut` (selector `0x5cefcf9b`, found with `forge selectors find`), the router bubbles it up, and the hook skips correctly, but dust crowded out real fills. An earlier note called this a router error; it is our guard. Sizes are 200 to 2,000 units for traders and 1 to 500 for the arbitrageur, so repeats of the same size are refused by the band (F03, PROGRESS).
- `PoolManagerShort` skips are expected, not a bug: when the pool's MUMB has been bought out (a sample shows `available` = 4 wei), a MUMB-in hint exceeds what the PoolManager holds and the hook skips (D-20). In the F08 setup this is the only skip that is not a band skip.
- No pass/fail guard on per-run counters. Foundry resets state between invariant runs, so a counter guard in `afterInvariant` would fail by chance. The counters are logged, with process-level totals across runs (via `vm.setEnv`, which the reset does not touch), and non-vacuity is the deterministic `test_F08_handlerReachesFillAndSkip`.
- "Within the band" statistic (PROGRESS only): the share of swap calls that began with the pool price within the band of Priya's live marginal price, taken as the ratio of her virtual balances (fee ignored). It decides nothing.
- `testFuzz_F08_fullAquaFillAnchorRecovers`, as built. Fill 100% of one size (300 to 1,000 units) until the band refuses; the refused swap is probed inside a snapshot and reverted, because a refused Aqua leg falls back to the pool filling everything, which moves the price (the first version asserted "a 100% hint never moves the pool" and failed on exactly that). Then one pool-only arbitrage swap with `sqrtPriceLimitX96` at Priya's marginal price, `sqrt(v1 * 2^192 / v0)` from her virtual balances, and the same 100% fill must go through. The arbitrageur's input is 5,000 units, far more than the move needs (about 700 units per 1% of price on this seed), because the limit stops the swap; 500 units left the pool about 1% short of her price, still inside the band, but a 1,000-unit fill has about 1% slippage of its own and was refused (2.01% against 2%).
- The band judges a fill's own price, not the pool's distance from Priya's marginal price: with the pool inside the band of her marginal price, a fill can still be refused once its slippage is added. So the property is stated as "arbitrage to her price, then the refused fill goes through", not "the pool was outside the band before".
- Untyped literal trap: `500 * (cond ? 1e6 : 1e18)` types the ternary as `uint64` and overflows; the test casts to `uint256` first.
- Run counts depart from the spec's "default run count", on purpose, and the team accepted 64 runs x depth 50 (3,200 calls) for the invariants and 64 runs for each fuzz test. The spec asks for a fixed seed and the default counts (256 runs, depth 500). Every run here is a fork run with real swaps, and the invariant campaign alone took about 4.5 minutes at 64 x 50, so the default 128,000 calls would be about 40 times that, roughly three hours; it was not run. The counts are held by the inline `forge-config` on the contract and are mutation-checked (each of the four properties goes red under an injected bug, see PROGRESS). The seed is not in the file; it is passed on the command line (`--fuzz-seed 0xf08`). The campaign passed three times with seed `0xf08`; call counts vary between runs, cause unknown, so the seed is not claimed to make the campaign reproducible.
- `fullAquaFillAnchorRecovers` sizes are 100 to 400 units and the test requires at least two fills before the band refuses ("many 100% Aqua fills" in the spec). With 300 to 1,000 units it often saw only one.
- What `testFuzz_F08_splitNeverWorseThanPoolOnly` does and does not show. It holds for this configuration: Priya's flat fee (0.30%) equals the pool's, and the pool sits at the anchor price, where her far deeper curve gives the trader a better price on any part of the input she fills. It is **not** a guarantee of the hook: the hook fills whatever the strategy and the band allow, and with a worse strategy the split is worse while the hook behaves correctly. Mutation 4b shows this: shipping Priya's strategy with a 3% fee makes the test go red (`1935992727 < 1936813904`) with nothing wrong in the hook. The guarantee a trader gets comes from the off-chain quoter (F07): `searchHint` always simulates hint 0 (pool-only) and ranks it with the other hints, and takes the best output (`scripts/src/quoter.ts`, `searchHint`), so the hint it returns is never worse than pool-only in simulation.

## D-29 V2-01: SplitMath overflow envelope, rounding rule, fallbacks and test tolerances (Nov 11, 2026)
- **Overflow envelope** (the spec asks for this entry): every reserve `x`, `y` and the amount below 2^128, and at most `MAX_VENUES` = 8 venues. Outside it the result is pool-only (index 0 gets the whole amount, makers zero). Inside it no intermediate overflows; the bound sits next to each product in the NatSpec (largest: `S2 < 2^255`, exact-in, a fee of 1e9 - 1). Never reverts: `testFuzz_V201_neverReverts` uses raw uint256 values biased to 2^128 ± 2, any uint32 fee and lengths 0 to 10.
- **Rounding rule** (the spec asks for this entry): the D-28 integer policy. `k = floor(sqrt(g·1e9·x·y))` (exact in) and `c = floor(sqrt(floor(x·y·1e27/g)))` (exact out) are bit-identical to the reference's `isqrt`. Every other rounding makes a share no larger than its exact value: exact in carries `S1 = Σ x/g` (floor) and `S2 = Σ k/g` (ceil) at 2^64 extra precision, so only the final floor matters; exact out rounds the subtracted `c·(ΣY − B)/Σc` up. Makers (index ≥ 1) get those floored shares; **index 0 (the pool) takes `amount − Σ makers`**. The spec's "a[last] (by convention the pool, index 0)" is read as index 0, as in the vectors. When one venue is active the closed form is exactly the amount, so that path skips the arithmetic. Result: every case in `split_2v`, `split_3v` and `split_caps` matches the reference **to 0 wei**, both modes. A first version without the extra precision lost about 2 wei per maker to the pool; that dust, priced at a worse rate, broke the literal bound below by 10 wei, which the reference policy does not.
- **[VERIFY]-style source checks** (V2-01 carries no [VERIFY] tag): `FullMath.mulDiv` at `lib/v4-core/src/libraries/FullMath.sol:14` (floor; reverts on a result ≥ 2^256 or a zero denominator). **No pinned library has a 512-bit square root:** OZ v5.4.0 `Math.sqrt` (`Math.sol:492`) and solmate's take a uint256, but the radicand reaches about 2^316 (exact in) and 2^346 (exact out) inside the envelope. So `SplitMath.sqrtMulDiv` runs Newton's method from above, `z ← (z + mulDiv(a, b, d·z))/2`, seeded at `(√(a/d)+1)(√b+1)` (at most 4× the root), bounded by `SQRT_MAX_STEPS` = 16. `testFuzz_V201_sqrtIsFloor` checks `z²·d ≤ a·b < (z+1)²·d` in 512 bits. SwapVM facts for the tests' totals: fee scale `BPS = 1e9` (`Fee.sol:17`), exact-in fee rounded up (`:89`), exact-out gross-up rounded up (`:95`), XYC out floor and in ceil (`XYCSwap.sol:22`, `:28`). A SwapVM fee may be 100% (`Fee.sol:29`), so a venue with `feeE9 ≥ 1e9` is unusable and gets zero.
- **Degenerate inputs, where the reference raises `InfeasibleError`:** an empty array gives an empty result; amount 0 gives zeros; `x = 0`, `y = 0` or a fee of 100% or more gives that venue zero. When the venues still free cannot fill what is left (no usable venue, or an exact output at or above their reserves), they get zero, **makers already pinned keep their caps**, and the pool takes the rest. With nothing pinned that is pool-only. This replaces the plan's "pool-only when caps cannot fill": keeping the capped makers is strictly better and still respects every maker cap. Maker caps are hard; index 0 may end past its own cap and, in exact out, past its own reserve. V2-02 reads that as "the pool crosses into its next range"; for a plain constant-product venue it is infeasible, and the hook (V2-07) must not send it as such.
- **What "relative error < 1e-9 against the vectors" is measured on:** each allocation within `amount·1e-9` of the vector, exactly 0 where the vector has 0, and the total recomputed with SwapVM's rounding within 1e-9 of `totalInt`. Measured deviation: 0 wei everywhere. Extra `test_V201_matchesV1DemoClosedForm`: the v1 pool's integer segment (capped at `capIn`) plus Priya. 1,000 USDC → 551,312,543 to Priya, exactly the vector; MUMB → USDC differs by 2e-10 relative, because the vector used Decimal pool reserves and the solver gets the floored integer segment (USDC side about 8e10 raw).
- **`neverWorseThanAnySingleVenue` tolerance (decided with Adityaraj before coding).** The literal "minus `v.length` wei" fails under the spec's own rounding rule when one input wei buys about 1e12 output wei (USDC → MUMB): a probe of the reference policy, with the pool's exact share a fraction of a wei, found the split 13 wei (X = 1e11) and 1,939 wei (X = 1e9) worse than the best single venue with n = 2; 18/18 decimals stayed within 1 wei. So there are two tests. (a) `testFuzz_V201_neverWorseThanAnySingleVenue`: literal `v.length` wei on comparable prices (reserves 1e9 to 2^112, y/x in 1e-3 to 1e3, fee ≤ 10%, half the makers capped). The reference policy passed 3,000 sampled cases there. (b) `...AnyPrice`: reserves 1 to 2^128, any price, slack `v.length` wei plus `v.length` wei of the allocated token at the highest marginal rate a venue reaches (exact in: the best starting rate; exact out: each venue's marginal cost at its share + `v.length`). A Python run of the reference policy over that domain stayed below 0.34 of the slack. In exact out the pool's floored remainder can reach its own reserve whenever the exact optimum leaves the pool under `v.length` wei of reserve: a dust-sized pool (Python: Y0 = 1, 302, 1,144 wei) or a trade that nearly drains every venue (found on comparable prices: pool y0 about 1.5e8 against an output of 7.9e27). The first version allowed it only in (b); the counterexample showed the premise was wrong (commit `96e6548` went in with that test red, fixed in `bf2df32`). Both modes; each leg is priced on the exact curve with one floor (exact in) or one ceil (exact out); single venues count only if their cap allows the whole amount.
- **`equalMarginals`** checks `(x + g·a)/√(g·x·y)` (exact in) and `(y − b)·√g/√(x·y)` (exact out), which are equal across free active venues, within 5e-7 (1e-6 on the marginal, which goes as 1/h²). ## D-30 V2-02: PoolVenue step-exact walk, piecewise solve, and the D-29 carry-overs (Nov 21-22, 2026)
- **Range counting: step-exact** (chosen with Adityaraj before coding). One segment is one iteration of `Pool.swap`'s loop (v4-core `Pool.sol:344-436`) that has liquidity and width. v4 stops at the next initialised tick **or the edge of the 256-tick bitmap word**, clamped to MIN/MAX_TICK, and rounds each step on its own. So a word edge splits a liquidity range into two segments with the same liquidity, as in the V2-00 reference (D-28 reviewer fix). Steps with no liquidity (a gap) or no width (the price exactly on a tick, such as the zero-for-one edge stop at tick 0) make no segment but still apply the tick's `liquidityNet`. Result: quotes built from the segments equal the chain **to the wei** in every test, both modes, both directions, with and without a protocol fee. The spec allows 2 wei per crossing; measured 0.
- **Two bounds:** `MAX_TICK_RANGES` = 8 segments (it is `SplitMath.MAX_SEGMENTS`, so the walk and the solver cannot disagree) and a new `MAX_TICK_STEPS` = 16 steps, empty ones included, so a pool full of gaps or word edges cannot make the walk read without bound. Both proposed in ARCHITECTURE-v2 section 5; V2-11 fixes them.
- **`truncated` and the hard-cap rule (amended after the spec review, chosen with Adityaraj):** `truncated` is true whenever the walk stopped at a bound (8 segments or 16 steps) before the trader's limit, whatever the liquidity there. Then `venues` leaves the last segment uncapped ("the pool takes the rest", ARCHITECTURE-v2 section 3; the real swap goes on past it). **The only hard end is the trader's limit.**
  - Why: the first version also required liquidity > 0 at the stop and hard-capped a stop with none, as if the liquidity had ended. Within the bounds the walk cannot tell a gap from that end. `spec-reviewer` found that with a gap right after the 8th segment, the piecewise solve pinned the pool at its walked capacity and pushed the rest onto makers, which can be worse than pool-only.
  - `test_V202_gapAfterWalkIsTruncated` (red first, `5a3a0d4`) builds that pool: deep liquidity to tick -480, one spacing of gap, deep again from -540, and a thin maker. Under the old rule the pool was pinned at exactly 252110146748779038157 (its walked capacity), and the maker took the whole remaining 1e20. Now the maker takes 6.4e18, and the split's output (339134423984614197606) beats the real pool-only swap (339019499049294625588).
  - Cost: at a real end of the liquidity within reach, the pool's share past it is not filled (a partial fill, as pool-only), where the makers could have taken it. Over-predicting the pool this way is never worse than pool-only: the pool fills what it can and the makers' legs only add.
  - Not covered: under-predicting. If the pool beyond a truncated walk is deeper or better priced than the last segment's curve, the makers can get flow the real pool would have beaten. That error is bounded by the curve's mismatch, not by a hard cap. PROGRESS carry-over (c) gives it to V2-07 and V2-10.
- **Spec deviation: `TickBitmap.nextInitializedTickWithinOneWord` is ported.** It takes `mapping(int16 => uint256) storage` (`TickBitmap.sol:85-90`), so it only runs on the PoolManager's own storage. `PoolVenue.nextInWord` is the same maths on a word read with `StateLibrary.getTickBitmap` (whose `int16 tick` argument is the word position, `StateLibrary.sol:201-213`), with v4's `compress`/`position` and `BitMath`, and v4's unchecked arithmetic. `testFuzz_V202_nextTickMatchesTickBitmap` checks it against the original on a harness mapping: any word, tick, spacing and direction.
- **Fee:** `swapFee` is `Pool.swap`'s fee for the direction: `lpFee` when that direction's protocol fee is 0, else `ProtocolFeeLibrary.calculateSwapFee(pf, lpFee)` (`Pool.sol:286-308`). The protocol's share comes out of the fee, so the trader's amounts depend only on `swapFee`. `feeE9 = swapFee · 1000`. **It reads `lpFee` from slot0, so it assumes the hook returns no LP-fee override from `beforeSwap`.** This is now a CLAUDE.md hard rule and a PROGRESS carry-over for V2-07.
- **Segment amounts:** `capIn` = `mulDivRoundingUp(getAmount{0,1}Delta(.., true), 1e6, 1e6 − fee)`, which equals `computeSwapStep`'s `amountIn + feeAmount` at the target (`SwapMath.sol:66-74`) and the reference's `_segment`. `capOut` = `getAmount{1,0}Delta(.., false)`. `x`, `y` are the virtual reserves at the start price, floored. Bounds for L < 2^128: `capIn` < 2^244, `x`, `y` < 2^192.
- **Never reverts; empty inputs:** an uninitialised pool, `swapFee ≥ 1e6` (v4 reverts on exact output there, `Pool.sol:311-316`) or a limit v4 would reject (`Pool.sol:322-338`) gives an empty segment list. Quotes clamp amounts above `type(int256).max`. In the piecewise solve, amount 0 gives zeros; more than 8 segments or more than 7 makers gives pool-only (as D-29's envelope); an empty pool puts an unusable venue (x = y = 0) at index 0, so the makers solve alone and index 0 takes only the remainder.
- **Piecewise API:** overloads `solveExactIn/Out(Venue[] pool, Venue[] makers, uint256 amount) → (uint256[] a, uint256 crossed)`, with V2-01's single-array functions unchanged. `a[0]` is the pool's total, `a[1 + j]` maker j's. `crossed` is the number of segments the pool's share fills completely (the vectors' `rangesCrossed`).
  - Pass k solves segment k plus the makers for what is left. A segment that is not the last is solved **uncapped** and compared with its cap: a share **≥** the cap crosses (its cap joins the prefix). The last segment is solved with its cap, so at a hard end the makers absorb what the pool cannot give.
  - Equivalence with the reference's capped solve: a capped solve pins the pool only when its share in some pass exceeds the cap, and the pool's share only grows from pass to pass (pinning makers raises the level). So solving uncapped and comparing makes the same decision with one pass less. Mutation M12 (every segment solved with its cap, the reference's literal form) survives, as this predicts.
  - `crossed == pool.length` happens only with a hard last cap, which from PoolVenue means the walk reached the trader's limit. The share is then exactly the walked total when the makers take the rest (`test_V202_hardLastCapPinsPool`), and more than it only when no maker has room. That last case is PROGRESS carry-over (a) for V2-07.
- **D-29 carry-over 1 (exact output past a range's reserve):** a share past a segment's reserve `y` is past its `capOut` too (`capOut ≤ y`), so it crosses. `test_V202_exactOutPastReserveCrosses` first shows V2-01's single-curve solve putting a 302-wei range past its reserve, then the piecewise solve crossing into the next range. ## D-31 V2-03: anchor fixed-point format, exp2 method, rounding, and the choices the spec left open (Nov 22, 2026)
- **Format.** One packed slot per pool, `Anchor { uint40 lastTimestamp; uint64 lastBlock; int24 snapTick; int56 emaTickX }` (184 bits; bits 184 to 255 stay 0, a test checks it). `emaTickX` is tick × 2^16, |value| < 2^36. The decay factor is Q128 (`2^128` = 1). The mapping is the hook's only state variable, so a pool's word is at `keccak256(poolId, 0)`; the tests read it with `vm.load`.
- **Update.** `ema' = snap·2^16 + ((ema − snap·2^16) · f) / 2^128`, with `f = 2^(−dt/H)`. The multiplication is on the deviation, below 2^38 × 2^128 = 2^166. **Signed division truncates toward zero**, so a deviation shrinks toward the snapshot by the same rule from above and below: `next(−s, −e) == −next(s, e)` exactly (fuzzed over the full tick range), the result is between the old EMA and the snapshot (so `emaBounded` holds by induction), and dt = 0 leaves the EMA exactly unchanged. A floor (`>>`) would leave a negative deviation stuck one unit below the snapshot; `test_V203_emaRoundsAroundZero` shows −1 unit going to 0, and mutation M1 is caught by 8 tests.
- **exp2 method.** `dt = q·H + r`; `f = 2^(−r/H) >> q`. The fraction `x = r/H` is taken to 32 bits (`(r << 32) / H`) and `2^(−x)` is the product, over the set bits i of x, of `C_i = floor(2^128 · 2^(−2^−i))`, i = 1 to 32, unrolled (no loop). Constants generated with Python stdlib `decimal` at 100 digits: `C_i = int(Decimal(2)**128 * Decimal(2)**(-(Decimal(2)**-i)))`, printed as the Solidity steps (the script is not committed; the 32 lines are in `AnchorLib.sol`, checked by the chain test below). Error: cutting x to 32 bits costs at most 2^−32·ln 2 relative, under 0.0003 of a tick over the whole range; each product floors by one Q128 ulp. `H` must be in [1, 2^32].
  - Tests do not use typed-in values: `dt = H/2` equals `Math.sqrt(2^255)`; `dt = kH` equals `2^128 >> k` exactly (k = 1 to 15, four values of H); every constant is isolated by `decayX128(2^(32−i), 2^32)` and `C_i²/2^128` is within 3 ulp of `C_(i−1)`, from `C_0 = 2^127`. Fuzz: monotonic non-increasing in dt, and `f(a+b) = f(a)·f(b)` to 2^−30 relative (below the cut-off).
- **Cut-off.** `dt >= 16·H` gives 0 (EMA = snapshot). The factor jumps from 2^−16 to 0 at that point, so the EMA moves by up to `|gap|/2^16` ticks at once (at most about 27 ticks over the full 1.77M-tick range). Accepted, as the spec says. My first accuracy fuzz hit this at a + b = 16H and was wrong, not the library; it now stays below the cut-off.
- **`emaTick` rounds to the nearest tick, ties up** (`(emaX + 2^15) >> 16`; chosen with Adityaraj). Every tick's bucket is 2^16 wide on both sides of zero (tested at −3 to +3 and at ±MAX_TICK). The alternative, a floor, would show an EMA just under the snapshot as `snap − 1`.
- **V2-04 compares in fixed point (Adityaraj's instruction).** The drift check must compare `snap × 2^16` with `emaTickX`, not the rounded `int24 emaTick`, so rounding never decides a refusal. `anchorOf` returns the rounded tick for display and for outside readers; V2-04 therefore needs the unrounded value from the hook (a second view or a wider return), which is V2-04's interface decision, recorded as a PROGRESS carry-over.
- **`anchorOf` reverts `PoolNotInitialized` when `slot0.sqrtPriceX96 == 0`** (Adityaraj's instruction), instead of returning (0, 0, false): tick 0 is a valid price (1.0), so zeros could pass V2-04's band check for a wrong pool key. It reverts in both paths that read `slot0`, the lazy view and `beforeSwap`'s update (the PoolManager checks first in a real swap, so the second matters only for a direct call). A pool stored this block is initialised, so that branch needs no read. `test_V203_anchorOfRevertsUninitialised` also checks that nothing was stored.
- **First touch is `lastBlock == 0`** (block 0 never has swaps). `dt` is the difference of the `uint40` timestamps modulo 2^40, so a wrapped timestamp still gives the true gap (tested: from 2^40−1 to 2^40+H−1 gives dt = H). Block numbers of 2^64 or more are unsupported (the test uses `type(uint64).max` as the last).
- **Event.** `AnchorUpdated(poolId, snapTick, emaTickX, timestamp)` on the first swap of a block only (chosen with Adityaraj, following the "event for every state change" rule). Gas, measured as the hook pays it (`V203GasTest`, one swap of 100 USDC through the PoolManager, every account and slot cold, hooked pool minus the same swap on the unhooked twin): **first-ever touch +30,950; first swap of a block (update of a stored anchor) +16,421; later swaps in the block +7,236**. Breakdown of the update: SLOAD of the anchor 2.4k (cold), `getSlot0` about 2.0k (the PoolManager has just read that slot, so it is warm), `AnchorLib.next` 2.8k (3.4k at dt = 59, most fraction bits set; 0.4k on first touch), SSTORE 3.2k (2.9k, nonzero to nonzero), event 2.0k, then dispatch, `toId`, memory and the call (cold hook account 2.6k plus the PoolManager's encode and decode, 3.9k, the same in all three cases). A first touch writes zero to nonzero: SSTORE 20.3k. **The 54,368 first logged here was wrong**: it was a direct pranked call from the test contract after a snapshot revert, so it was a first touch, not an update ("over a slot that already holds an anchor" was false), and a state-changing call made by the test contract itself costs about 20,000 more than the same call through another contract (probe SSTORE: 46,177 direct, 26,370 through a relay; cause not isolated, reproduced on an unrelated probe, so it is the harness, not the hook). V2-11 sets the budget from the in-swap numbers.
- **v2 hook deploy.** `ForkBase._deployHookV2()` (mined with `HookMiner`, same flags as v1); `setUp` does not call it, so v1 tests do not pay for it (chosen with Adityaraj; the spec said "next to v1's", whose deploy is in `PoolBase`). `V203AnchorTest` extends `PoolBase`, so a v1 hook and pool also exist there; they are unused.
- **Source checks** (v4-core under `contracts/lib/`): `PoolManager.swap` calls `key.hooks.beforeSwap` (`PoolManager.sol:200`) before `_swap` (`:204`); `slot0`'s tick is written only by `Pool.initialize` (`Pool.sol:106`) and `Pool.swap` (`:439`), so liquidity changes and donations never move it and "every price change is a swap" holds; `Hooks.beforeSwap` skips the hook when `msg.sender == address(self)` (`Hooks.sol:252`), so **the v2 hook must never call `PoolManager.swap` itself** (a constraint on V2-05 to V2-08: its own fills go through the router, not through a pool swap); an LP-fee override is parsed only for dynamic-fee pools (`Hooks.sol:262`) and `beforeSwap` always returns 0 (D-30). `slot0.tick` ranges over [MIN_TICK, MAX_TICK − 1]: limits must lie strictly inside the price bounds (`Pool.sol:322-338`). `MAX_TICK` itself is unreachable, so the test writes that word by hand to show the packing holds. Not a [VERIFY] item: V2-03 has none.
- **Pool-only.** `beforeSwap` returns `(selector, ZERO_DELTA, 0)`. `test_V203_poolOnlyUntilV207` compares four swaps (exact in and out, both directions, across the first touch, the same block and the next block) with an unhooked twin pool from one snapshot: equal deltas, hook holds nothing. It passes against the red stub too (pool-only holds without an anchor); the anchor tests are what went red.
- **Mutation checks** (5, each applied, the V203 suite run, then restored; tree clean afterwards): **5 caught.** M1 `>>` instead of truncating division (8 tests: emaBounded, mirror, deep negative, rounds-around-zero and more); M2 `emaTick` truncates (`emaTickRoundsToNearest`); M3 the lazy view skips the decay (`emaHalfLife`, `packingRoundTrips`, `viewEqualsStored`); M4 `<=` for `<` in `beforeSwap`, refreshing on every swap (`snapshotFixedWithinBlock`); M5 constants C_7 and C_8 swapped (`exp2ExactPoints`' chain and the accuracy fuzz).
- **Lint and format:** the files' casts carry `forge-lint: disable-next-line(unsafe-typecast)` (each bounded by the maths above); tests use `vm.getBlockNumber()` and `vm.getBlockTimestamp()` after `vm.roll` and `vm.warp` (the `environment-read-across-mutation` lint).
- **`anchorOf` and pools that do not use this hook (spec-reviewer note, Nov 22).** `anchorOf(poolId)` cannot tell which hook a pool has. For an initialised pool that does not use this hook, the anchor is never stored, so every call takes the lazy path and returns the current spot `slot0` tick as both snapshot and EMA (`fresh = false`). `PoolNotInitialized` covers only pools with no price. **So V2-04's BandGuardV2 must derive the `PoolId` from the `PoolKey` and call `anchorOf` on `key.hooks`, and never accept a bare `PoolId`.** A key whose `hooks` is this hook always names a pool that uses it, so the anchor is real; a bare id could name any pool and make the guard read spot, which the hard rule forbids.
- **NatSpec on the nine unused callbacks** (`.claude/rules/solidity.md`: every external function says who may call it): each now says it always reverts `HookNotImplemented`, that anyone may call it to no effect, and that the PoolManager never does.


## D-32 V2-04: BandGuardV2 args, the drift unit, price scale, the anchor read, and gate M2 (Nov 22, 2026)

- **Price scale: adaptive** (chosen with Adityaraj). Both prices are currency1 per currency0. With `s = getSqrtPriceAtTick(snap)`: if `s < 2^127`, `ref = s·s` (X192, exact, below 2^254) and `exec = num·2^192/den`; else `ref = mulDiv(s, s, 2^96)` (X96, in [2^158, 2^224)) and `exec = num·2^96/den`, with `num/den = amountOut/amountIn` (currency0 in) or `amountIn/amountOut` (currency1 in). `exec` is `type(uint256).max` when `num >> (256 − shift) ≥ den` (the true price is at least 2^256, more than twice any `ref`), so no overflow and no panic. ## D-33 V2-05: template T1, the registry, depth and its price source, and the choices the spec left open (Nov 22, 2026)
- **Supersedes D-09 and D-18** (one order per pool, any maker can displace it). Up to `MAX_STRATEGIES` = 6 slots per pool, one per maker. Only the maker can `unregister` or replace its own slot; `evict` works only on a docked strategy or one with zero depth; a newcomer displaces a live slot only with strictly more depth (`test_V205_noDisplacement`, `slotsAndEviction`).
- **`Params.salt` is `uint64`** (chosen with Adityaraj; the spec said `bytes32`). The 1inch SDK 0.4.0 encodes `_salt` as 8 bytes (`SaltArgsCoder.addUint64`, asserts at most 2^64 − 1), so only a `uint64` can match the SDK byte for byte. Salt 0 leaves the `_salt` step out. SwapVM ignores the salt's args (`Controls.sol:70`). The V2-05 spec line is changed to match.
- **Template bytes are checked against the SDK, not against our code.** `reference/sdk/gen_t1.ts` (run with `scripts/node_modules/.bin/tsx`, imports the installed SDK and viem by path; `scripts/` is untouched) writes `contracts/test/sdk-vectors/t1_sdk.json` (not `test/vectors`, which `test_V200_vectorsLoad` asserts holds exactly the five generator files; `foundry.toml` gets one more read-only `fs_permissions` entry, approved by Adityaraj): three parameter sets (no salt; salt 1, fee 0, band 1, drift 0, open; salt 2^64 − 1, fee 1e9 − 1, band 10,000, drift 10,000). Guard args are packed with viem, not with our Solidity. Output is byte-identical on rerun (sha256 `3693c498…`). `test_V205_templateMatchesSdk` compares program bytes, `abi.encode(order)` and the hash.
- **Opcode indices are constants in `StrategyTemplate`** (salt 20, flat fee 21, XYC 17, Extruction 32), chosen with Adityaraj. A pure library cannot call `AquaOpcodes._opcodes()` (internal to a contract), and inheriting it would compile the SwapVM instruction set into the hook. `test_V205_opcodesFromAquaOpcodes` asserts each equals `ProgramBuilder.findOpcode(_opcodes(), ...)`, and the SDK fixture pins them again, so "never typed in from docs" holds: they are looked up and tested, not trusted.
- **The hook rebuilds the order** (chosen with Adityaraj). `register(PoolKey, Params)` builds the T1 program with `key.hooks = address(this)` and the hook's own `bandGuard`, builds the order for `msg.sender`, hashes it, and asks Aqua. A maker cannot choose the guard args, so the key inside them always equals the registered key (carry-over 1). A maker who ships a program with another `hooks`, currency order, fee, tick spacing or exclusive flag ships a different hash, and `register` finds nothing shipped (`rejectsForeignProgram`, one case per field). The args' `poolManager` field is passed (the hook's own) but nothing reads it back (carry-over 2).
- **Key errors, one named error each, checked in this order:** `HooksMismatch(hooks)`, `NativeCurrencyUnsupported` (Aqua has no native balances), `CurrenciesOutOfOrder` (also for equal currencies), `InvalidPoolFee(fee)` (above `MAX_LP_FEE` and not the dynamic flag), `InvalidTickSpacing(spacing)` (outside 1 to 32,767, `TickMath`), then `PoolNotInitialized`. A valid but wrong fee or spacing names another pool, which the hook can only see as uninitialised, so both give `PoolNotInitialized` (tested).
- **Status check.** Aqua's `rawBalances` returns the token count (`Aqua.sol:26`, `libs/Balance.sol:10`): both tokens must report 2. Both 0xff is `StrategyDocked(hash)`; anything else is `StrategyNotShipped(hash)`. That covers never shipped, another app (the hook asks for `ROUTER` only), another token pair, three tokens (count 3), another maker (Aqua keys by the sender). `AQUA` and `ROUTER` are constants in the hook, the same addresses on Ethereum and Unichain (D-28). The hook deploys its own `BandGuardV2` in its constructor (`bandGuard`), so the mined-address deploy helper is unchanged.
- **Depth.** Per token: min(Aqua virtual balance, wallet balance, `allowance(maker, AQUA)`), which is what Aqua's `pull` can move (`Aqua.sol:63-70`). The two tokens are valued in currency1: `d0 · price + d1`. This only ranks slots; V2-06 computes the cap per fill. One strategy per maker per pool, so one wallet's funds count once per pool (`oneWalletCountsOnce`). **Depth ranks slots only within one pool. A wallet that backs strategies in several pools counts fully in each. Accepted: V2-06 caps fills per swap, not per wallet.**
- **Price source (changed after plan review): the stored snapshot, never spot.** `_anchorNow` is a private `view` and writes nothing (checked), but before a block's first swap it computes the snapshot from the current `slot0`, which is movable inside one transaction, so depth must not use it. Depth uses `_anchors[id].snapTick`, the tick recorded at the start of the last block that had a swap. **A pool with no recorded anchor has no price: `register` and `depthOf` revert `AnchorNotInitialised`** (any first swap, however small, creates it; no other source is used). The cost: a maker cannot register before the pool's first swap. The snapshot can be old (nothing is recomputed from spot); that only makes ranking coarse, never manipulable in the transaction. `test_V205_depthIgnoresSpotAndNeedsAnchor`: a fresh pool reverts; after the anchor, a push of more than 200 ticks in the same block changes no slot's depth, and a newcomer that would win at spot (worth 990 MUMB at the snapshot, over 1,000 at the pushed spot) is refused with the snapshot value.
- **Depth maths (overflow).** `depthValue` multiplies by `sqrtPrice / 2^96` twice with `FullMath.mulDiv`, each step saturating to `type(uint256).max` when `x · s >= 2^352` (checked with `Math.mul512`, so `mulDiv` never reverts), and the final sum saturates. Two saturated values tie, and a tie never evicts. `test_V205_depthValueExtremes` at MIN_TICK and MAX_TICK, amounts up to `uint128` max (and `uint248` max for saturation): no revert; token1 outranks token0 at the minimum price and the reverse at the maximum.
- **Eviction rule.** When full, the smallest live depth (lowest index on a tie) is the candidate; a newcomer needs depth strictly greater. The reason is `DOCKED` or `NO_DEPTH` when the smallest slot is dead, else `DISPLACED`. `evict(key, maker)` is open to anyone but only for docked (both tokens 0xff) or zero depth, else `NotEvictable`. A maker who registers again replaces its own slot in place and emits `MakerUnregistered` for the old hash. Registration needs depth above zero (`NoDepth`). Removal is swap-and-pop, so slot order carries no meaning. Every loop runs to `min(length, MAX_STRATEGIES)`.
- **`driftTicks` bound.** 0 to 10,000, from `BandGuardArgs.MAX_DRIFT_TICKS` (`BandGuardV2.sol:49`), enforced by `_validate` (`:91`) and recorded in D-32. Neither the V2-04 nor the V2-05 spec states it. The template builds its args with `BandGuardArgs.build`, so it accepts exactly what the guard accepts. `driftTicksEdges` registers 0 and 10,000; 10,001 reverts `InvalidDrift`. The band bounds (1 to 10,000) and a fee of 100% or more (`InvalidMakerFee`; SwapVM allows 100% but it can never fill, D-29) are in `templateBounds`.
- **Events.** `MakerRegistered(poolId, maker, strategyHash, params, depth)`, `MakerUnregistered(poolId, maker, strategyHash)`, `MakerEvicted(poolId, maker, strategyHash, reason)`; `poolId` and `maker` are indexed. Storage: `_slots` is declared after `_anchors`, so V2-03's tests still find the anchor mapping at slot 0.
- **Unichain.** The v4 PoolManager there is `0x1F98400000000000000000000000000000000004` (24,050 bytes of code at block 63,605,700; the mainnet address has no code on Unichain). `test_V205_templateFillsOnUnichain` covers: template, real Aqua `ship`, `register`, `BandGuardV2` reading the hook's own anchor on a real v4 pool, and a fill with the hook's address as `msg.sender` and as taker (output asserted to the wei: maker wallet, Aqua virtual balances, the hook, the router, Aqua; an outside taker is refused). **Left for V2-07:** the hook calling the router from `beforeSwap`, `take`/`settle` with the PoolManager, approve and reset, try/catch, the returned delta. The hook's address is pranked and funded by the test here.
- **Sizes** (`forge build --sizes`, `ConfluenceHook`): runtime 13,941 B (margin 10,635 to 24,576), initcode 18,418 B (margin 30,734 to 49,152), both with the registry and the embedded guard's creation code. `BandGuardV2`: 3,811 / 3,837 B.
- **Mutation checks** (5, each applied to `ConfluenceHook.sol`, the V205 tests run, then restored; tree clean): **5 caught.** M1 hooks check removed (`poolKeyChecks`); M2 depth = virtual balance only (`phantomDepthCannotEvict`, `anyoneEvictsDocked`); M3 `<` for `<=` on eviction (`slotsAndEviction`); M4 a three-token strategy accepted (`rejectsForeignProgram`); M5 depth priced at spot (seven tests, among them `depthIgnoresSpotAndNeedsAnchor`).
- **Lint.** `forge fmt` and `forge lint` clean on the three code files. ## D-34 V2-06: MakerVenue reserves, caps, the band-cap margin rule, and the choices the spec left open (Nov 23, 2026)
- **Safe cap, not the literal edge** (chosen with Adityaraj; this changes the wording of `test_V206_bandCapMatchesGuard`). The guard checks integers: the output is floored, then the execution price is floored (`BandGuardV2.sol:195-203`). So the set of fills it passes is **not** a down-closed interval at the wei level. A Python model of the exact check (stdlib; not committed) showed: USDC -> MUMB (6 -> 18) at the fork price, root = largest passing amount with no holes; 18/18 decimals at tick 0, root - largest passing = 24 wei (token0 in) and 14 wei (token1 in), with holes below; MUMB -> USDC (18 -> 6), within about 50 output levels (2.5e-8 relative) below the edge about 90% of each level fails. So "cap + 1 reverts" cannot hold in every regime. **`capIn` is the largest gross input such that every fill in `[capMin, capIn]` passes the guard**, found in closed form with no search. The spec's test becomes: `capMin`, `capMin + 1`, `capIn - 1` and `capIn` fill on the real router with the predicted output; the first power-of-two slack past the cap that the guard refuses is found and refused on the real router with `BandExceeded` (token0 in: 8 wei; token1 in: 2^48 wei, about 1.4e-7 of the cap). The dense and fuzz checks below are what stand behind "every fill in the interval".
- **Why the band cap needs `capMin` too.** The same output floor makes tiny fills fail: below about `1e4 / bandBps` output wei (about 50 at 200 bps) the floor eats the band slack, or the output is 0 (`BandNotComputed`). `Maker.capMin` is the smallest gross input the guarantee covers; V2-07 must drop a leg under it (or let the pool take it). A maker whose cap falls below `capMin` is `SKIP_UNDERFUNDED` if the wallet, allowance or PoolManager leaves less than `capMin`, else `SKIP_BAND`.
- **The margin rule and why it is sound.** Let `c = N / D` with token0 in `(ref - lim) / 2^s` and token1 in `2^s / (ref + lim + 1)` (`s` = the guard's scale, 192 or 96). A fill with net input `n` and floored output `o = floor(n y / (x + n))` passes the guard if `o >= ceil(c n)` (token0 in) or `o >= floor(c n) + 1` (token1 in); both are at most `c n + 1`. So **`n y >= (c n + 1)(x + n)` is sufficient, and its slack is concave in `n`**: if it holds at two nets it holds at every net between them. The library checks the integer form `ceil(c n) + 1 <= floor(n y / (x + n))` (which implies it) at the two ends and nowhere else. The other side of the band follows from the starting price: for token0 in the real exec price is below `y 2^s / x`, which `_startInBand` requires `<= ref + lim`; for token1 in it is above `x 2^s / y`, required `>= ref - lim`. Ends: `nMax = n_r - m` with `n_r = floor(y 2^s / N) - x` (the real root) and `m = 4 (x + n_r)^2 / (y n_r) + 2` (one output wei costs `(x + n)^2 / (y n)` of net input; the integer form costs up to two more, so four leaves room); `nMin = 4 x / (y - c x - 1) + 2` (first-order root, times four). **The factor 4 is empirical, not proved.** The 2x version failed (below) and 4x passes the 5,000-run fuzz, the fixed regimes and the X96 cases; no argument shows that 4x is enough in every regime. What is proved is the part that carries safety: the sufficient inequality, its concavity, and the exact integer check at both ends (so any cap the library returns passes the guard for every fill in `[capMin, capIn]`). If the factor is too small somewhere, the exact check fails and the maker is `SKIP_BAND` (liquidity lost, never an unsafe cap); V2-10 fuzzes it much harder (PROGRESS). **If either end fails the exact check, the maker is `SKIP_BAND`; the margin is never widened.** Gross amounts: `net(a) = floor(a (1e9 - fee) / 1e9)` (Fee.sol:86-91), so the largest gross for a net `n` is `ceil((n + 1) 1e9 / (1e9 - fee)) - 1` and the smallest is `ceil(n 1e9 / (1e9 - fee))`.
- **No exact-edge shortcut** (Adityaraj's instruction). The idea "when the margin is 0 or 1 wei, take `n_r` or `n_r - 1`" is not in the code: the model above found holes below the root even at 18/18 decimals, so nothing proves no gaps below `n_r` when the margin is small. The cap always comes from the rule above.
- **The rule was first at 2x and failed.** A first version used factors of 2 (`nMax`) and 2 (`nMin`). The integer check lost up to two output wei against the real inequality, so the rule sat exactly on the borderline: token1 in (the 18 -> 6 direction) at `bandBps` 1 returned `SKIP_BAND`. Factors of 4 fix it with the check unchanged. (The regime tests were red at that point; nothing was widened.)
- **How the rule is tested (the acceptance gate Adityaraj set).** (a) `testFuzz_V206_bandCapPasses`: **5,000 runs**, random tick (+-300,000), band 1 to 10,000, fee up to 50%, maker size 1e9 to 1e30, start price within half a band either side, both directions; the cap, `capMin`, their neighbours and four pseudo-random fills in between must all pass the real `BandGuardV2`. (b) Fixed cases, no randomness, both directions at `bandBps` 1, 200 and 10,000: USDC <-> MUMB at the fork pool's tick with 100,000-unit makers, a thin 1,000-unit maker on the same pair, and 18/18 at tick 0 (`test_V206_bandCapPassesRegime6to18`, which is USDC -> MUMB for token0 in and MUMB -> USDC (18 -> 6) for token1 in; `test_V206_bandCapPassesRegimeThinMakerBothDirections`; `test_V206_bandCapPassesRegime18x18AtTick0`). Each checks the first 150 and the last 150 integers of `[capMin, capIn]`, **50 output levels below the cap** (the first and the last input of each level; the last input is found by binary search on the output) and **50 output levels above `capMin`** (the last input of each level only: it is the worst case, since the guard's price grows with the input inside a level for token1 in and falls for token0 in, but the first input of a level above `capMin` is not checked). All pass. The 6/18 tick (276,324) is a file-level constant; `test_V206_regimeTickIsThePoolsTick` asserts it equals the fork pool's snapshot tick (slot0's tick at the block's first swap). (b2) `test_V206_bandCapPassesRegimeX96AndExtremeTicks` (added after the spec review): fixed cases at ticks 430,000 and 600,000, where the guard uses the X96 scale (sqrt price >= 2^127; the test asserts the scale), and at -430,000 and -600,000, where the price is tiny and the X192 scale holds (X96 only exists at positive ticks), both directions, `bandBps` 200, larger reserve 1e36; every one of the same density checks passes. The random fuzz (a) stays within +-300,000, so it never reaches X96; V2-10 does (PROGRESS). (c) `testFuzz_V206_mirrorEqualsGuardNearEdges` and `...WideRange`, 5,000 runs each, check `bandPasses` and `driftPasses` (the library's mirrors) against the real guard: the first puts the fill within one wei or a few ppb of the band's edge and the EMA exactly at, one unit inside and one unit outside `driftTicks * 2^16`, both signs; the second draws ticks over the whole range, sizes up to the full word (saturation) and any EMA near the snapshot.
- **Worst-case gap between the cap and the true (real-number) edge**, net input, from the regime tests' logs (relative to the edge): USDC -> MUMB, 100,000-unit maker: token0 in 6 wei (6e-7 at 1 bp, 2.9e-9 at 200 bps); token1 in (MUMB -> USDC) 4.0e16 wei at 1 bp (0.4%), 2.1e14 at 200 bps (1.0e-7), 1.6e13 at 10,000 bps (1.6e-10). Thin 1,000-unit maker: token0 in 6 wei (6e-5 at 1 bp), token1 in 4.0e16 wei at 1 bp (**40%**; only about ten output levels fit in a 1 bp band at 1e5 output wei, so a thin maker at 1 bp is nearly unusable and `capMin` is 67% of the cap), 2.1e14 at 200 bps (1.0e-5). 18/18 at tick 0: 40,010 wei at 1 bp (4e-15), 210 to 214 at 200 bps, 18 at 10,000 bps. At 10,000 bps token0 in has no lower edge (`ref - lim = 0`).
- **Status codes and the order of checks** (`readOne`): `SKIP_DRIFT` first (no external call; the guard's own drift rule, mirrored in fixed point), then the order is rebuilt from `StrategyTemplate.order(maker, program(params, pm, key, guard))` and its hash compared with the stored one (a mismatch is `SKIP_UNDERFUNDED`: Aqua would not know the bytes; carry-over 4), then `rawBalances` for the two tokens (count 2 on both, else `SKIP_UNDERFUNDED`: unshipped or docked), then `caps`. `caps`: fee at 100% or more, or a reserve above 2^128 - 1 (SplitMath's envelope, D-29), is `SKIP_MATH`; a zero reserve, output cap or PoolManager balance is `SKIP_UNDERFUNDED`; a starting price outside the band is `SKIP_BAND`. **The guard is two-sided**, so a maker priced above the market is dropped just like one priced below: a generous maker would only pass for large fills, which a cap cannot express (the lower bound). `SKIP_MIN_LEG`, `SKIP_REVERT` and `SKIP_GAS` are the hook's (V2-07).
- **`rawBalances` x2, not `safeBalances`** (`Aqua.sol:26`, `:30-35`): `safeBalances` is what the router uses at fill time and reverts for count 0 or 0xff, so a dead maker would revert the read. `rawBalances` never reverts and its count says which. Per maker: 2 Aqua reads and 1 `allowance` (output token only) plus 1 `balanceOf`; the PoolManager's balance of the input token is read once per `read`. `read` loops `min(len, MAX_MAKERS)` with `MAX_MAKERS` = 6, a test asserts it equals `MAX_STRATEGIES`. `test_V206_sixMakersBounded` pins, with `vm.expectCall`, 12 `rawBalances` calls (2 per maker), 6 MUMB `allowance` calls and 0 USDC `allowance` calls for 8 entries read as 6; it does not count `balanceOf` or the PoolManager read, so "nothing else" is not asserted. `toVenues` is bounded the same way (`Math.min(len, MAX_MAKERS)` in both loops; `test_V206_toVenuesReadsOnlyMaxMakers` passes 8 entries and gets only the first 6 looked at, no revert).
- **One shared min** (carry-over 1). `MakerVenue.real(token, maker, virtual)` = `min(virtual, wallet, allowance to Aqua)`; `ConfluenceHook._real` now calls it (the one edit outside the spec's file list, approved by Adityaraj; V2-05's 17 tests unchanged and green; the hook's runtime size is unchanged at 13,941 B). The cap uses it on the output token only: the input token needs no allowance (the router pushes it to the maker).
- **The virtual balance never binds as an output limit.** XYC's output stays below `y`, so `min(virtual, ...)` as a limit is either the wallet or the allowance, or the curve itself. The virtual balances enter through `x` and `y`: `test_V206_capFollowsWalletAllowanceAndVirtual` checks that `x`, `y` are Aqua's new balances after someone else's fill and that the cap moved.
- **The output cap, exactly.** With `O = real(tokenOut)`: the largest net with `floor(n y / (x + n)) <= O` is `ceil((O + 1) x / (y - O - 1)) - 1` (unbounded when `O + 1 >= y`), then the largest gross for it. `testFuzz_V206_capInversionIsTight` (2,000 runs): `out(capIn) = capOut <= O < out(capIn + 1)`. On the fork the router's own `quote` gives the same bracket for wallet, allowance and shared-wallet cuts (`_assertTightAt`), and a real fill at the cap succeeds with exact wallet, Aqua-virtual, trader, helper and hook balances.
- **PoolManager cap is per venue.** `capIn <= PoolManager.balanceOf(tokenIn)` for each maker, so the sum over makers can exceed it: V2-07 must enforce the total (v1's `PoolManagerShort` was per fill).
- **Quote = fill, to the wei.** `quoteExactIn` is `net = a - ceil(a fee / 1e9)`, `out = floor(net y / (x + net))`. `test_V206_predictionEqualsRouterQuote`: 5 sizes x both directions equal to `router.quote`; `test_V206_fillAtCapEqualsPrediction`: real fills at `capIn` and `capMin`, both directions.
- **`Maker.capOut` is already in the struct** (the output at `capIn`); V2-08 builds the exact-output venue from it. `toVenues` returns the live makers as `SplitMath.Venue` (cap = `capIn`, input units) and their indices.

- **Decision B: the exact-output safe cap (`MakerVenue.capsOut`).** SwapVM computes exact output as XYC `n(b) = ceil(b x / (y - b))` (`XYCSwap.sol:26-31`), then the fee grossed up, `gross = n + ceil(n f / (1e9 - f))` (`Fee.sol:92-96`), so `BandGuardV2` (which never reads `isExactIn`, `BandGuardV2.sol:118-146`) sees the NET input `n(b)` and the exact output `b`; the fee's ceiling is invisible to it. With `N(b) = b x + y - b - 1`: `n(b) <= N(b) / (y - b)` for every `b`. Token0 in (`c = lo / 2^s`): the guard passes if `2^s b (y - b) >= lo N(b)`; token1 in (`c = 2^s / (hi + 1)`): if `(hi + 1) b (y - b) > 2^s N(b)`. Both differences are concave quadratics in `b` (leading coefficient `-2^s` or `-(hi + 1)`), so holding at `bMin` and `bMax` they hold at every integer between; the far side of the band follows from `_startInBand` as in D-34. The ends come from the real edge `b_r = y - c x` with `m = 4 ceil(c y / b_r) + 2`: `bMin = m`, `bMax = b_r - m` (first-order roots, times four) and are **verified exactly in 512 bits** (`_okOut`); a miss is `SKIP_BAND`, so the factor of four only decides liquidity lost, never safety (as D-34). The spec review found that `4 ceil(c y / edge) + 2` overflows 2^256 near the top tick with a 1 to 3 wei maker (`c` about 2^128, `y` within a few wei of `c x`), which made `planExactOut` revert and the swap pool-only (`SKIP_PLAN`) while the NatSpec said "never reverts"; `test_V208_capsOutNeverRevertsAtExtremeTicks` reproduces it (panic `0x11`, red first) and `capsOut` now returns `SKIP_BAND` when the margin would not fit. The ranges are wide (`bMin / bMax` from below 1e-18 up to 0.67 across the regimes), so the check is not vacuous.

The hook's `walked >= B` is as strong as the hook can make it without a pool walk; a plan whose `walked`, `poolOut` or `poolOnlyOut` disagrees with a real quote is the D-35 accepted gap (the trader's own maximum input bounds it; an honest splitter cannot produce it). The splitter trims a leg whose gross input exceeds what is left of the PoolManager's balance to the output of an exact-input fill of what is left.
- **Decision F: a pool that cannot give B stays pool-only (carry-over, product gap).** The walk cannot tell the end of the liquidity from its own bound (D-30: a gap and the end look the same), so the pool is almost always reported truncated when it is short. A first version estimated the rest at the walk's end price (a lower-bound `tail`); a test showed the swap then blended and delivered all of B where pool-only gives a partial fill. Nothing beyond the walk is known, so the rule is now: **unless the walked segments give all of B, the swap is pool-only** (`SKIP_NOT_BETTER` on a planned leg), even when makers could cover the rest. This is also exactly what the hard rule "never worse than pool alone" can prove without a guess. It is a product gap (a large exact-output swap past the walk is never blended) recorded in PROGRESS.
